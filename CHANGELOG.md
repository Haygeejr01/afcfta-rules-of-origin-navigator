# CHANGELOG — build log

Real entries from the build, in the order they happened. Every "Evidence" cell is
something observed in a run or a test, not a prediction.

## Build stages

| Stage | What I tried and why | Evidence | Decision / Learning |

| **Model selection** | Spec called for Qwen 2.5 7B *instruct*. Only the **coder** variant (`qwen2.5-coder:7b`) and a 1.5B coder were on disk. Recorded as a real constraint rather than glossed as "we used Qwen 7B". |
| **Data before code** | Built `mock_tariff_db.json` and `synthetic_manifests.json` with full ground truth before writing a single node, so evaluation could never be tuned to fit the implementation. | 10 manifests, ground truth hand-computed. **All ten HS subheadings reviewed against HS-2022 and confirmed correct by hand before submission** — the dataset's real-code claim is checked, not merely asserted. | Held. Fabricating thresholds *and* presenting them as authoritative would be the one unrecoverable integrity error here. |
| **Ground truth needs a guard** | Hand-computed numbers rot the moment a manifest is edited. | — | Wrote `tests/test_ground_truth.py`: it recomputes every declared RVC% from the declared costs, re-derives every threshold from the rule table, and asserts each declared verdict against the real calculator. | **Money arithmetic** | Started with plain `float`. | With a ±2pp borderline band, verdicts hinge on tiny differences, and `4080/8000*100` is not exactly `51.0` in binary floating point. | Moved all sums and the division to `Decimal`, quantised once to 2dp. |
| **Rounding and verdicts must agree** | Realised a system could compute an unrounded 49.997, report "50.00%", and print "FAIL" beside it. | — | The **quantised** value is what gets compared to the threshold. A report reading "50.00% against a 50% threshold: FAIL" is now unreachable. Test: `test_reported_percentage_and_verdict_never_disagree`. |
| **Baseline fairness** (important) | The obvious baseline withholds the rule table and relies on the model's own knowledge. | Our thresholds are **synthetic** — no model could ever recover them. Withholding the table would guarantee a 0% baseline on every threshold. | **Pasted the full rule table into the baseline's single prompt.** Still one zero-shot call, no tools, no schema, no deterministic math. This makes the comparison about what the architecture adds, not about who memorised an invented number. Without this the whole evaluation would have been rigged. |
| **Baseline grading tolerance** | Needed a tolerance for RVC comparison. | Agent arithmetic is exact to 2dp. | Used **±0.5pp for both systems**. A tolerance can only ever help the baseline here, never the agent. |
| **Ran the baseline** | 10 manifests, one prompt each, temperature 0. | **HS code 9/10. RVC percent 0/10. Verdict 5/10.** Avg 37.8s, 1 call/case. | The finding I did **not** expect: the model is *good* at HS classification. Claiming classification as the architecture's win would have been false. |
| **Looked at *how* the baseline failed** | Read the raw responses instead of only the scores. | Every response was **three bare lines with no working**. M001: `RVC_PERCENT: 47.50%` (truth 79.41%). M008: `27.69%` (truth 67.32%). **And the decisive one: M002 and M010 came back byte-identical — `8544.42 / 37.00% / FAIL` — despite being a Moroccan wiring harness (true RVC 11.33%) and a South African solar module with a different component list, different origins and a different total cost.** | Asking for "two decimal places" produced *false precision*, not arithmetic. `27.69%` looks computed; it is fabricated. The duplicate pair proves it: one number for two unrelated bills of materials means the model was matching a plausible percentage to the **HS code**, not dividing one cost by another. This is the hot take (see README). |
| **Worst-case analysis, not just accuracy** | Checked the *direction* of each baseline error. | **M008: said FAIL, truth PASS** (67.32% vs a 30% threshold). **M004: said FAIL, truth PASS.** **M006: said PASS at 41.86%, truth 34.00% against a 35% threshold.** | Both error directions carry real cost: false negatives make an exporter abandon a valid preference claim; false positives lead to a rejected claim at the border. "5/10 verdicts correct" understates the damage — all 5 correct verdicts rest on a wrong number. |
| **Framework choice** | Considered LangGraph for the workflow. | Control flow is one straight line plus a single bounded loop back to `LOOKUP_RULE` on reviewer edit; the pause is a real process pause backed by a checkpoint file. | **Plain Python state machine.** A framework would add a dependency and an indirection layer without changing the control flow or the interrupt semantics. Revisit if the flow gains concurrent branches or needs distributed resumption. |
| **Retry / backoff** | Deliberately wrote the Ollama client with no retry, no backoff, no circuit breaker. | **10/10 baseline calls succeeded. 0 failures, 0 rate-limit responses, 0 unparseable JSON responses.** | **No retry code was added**, because nothing in evaluation justified it. If 429s or timeouts appear later, that is when the code changes — and this row is where the evidence would go. |
| **JSON parsing** | Considered a parse-and-retry loop for extraction. | Ollama's `format: json` constrains decoding at the grammar level. | No retry loop. Malformed JSON is *prevented*, not recovered from. Valid-JSON-but-wrong-shape still fails Pydantic and routes to human review, which is the correct destination for it. |
| **CLASSIFY_HS: prompt vs guarantee** | The prompt tells the model to pick only from the shortlist. | The baseline answered a **solar PV module with `8544.42`** — the adjacent electrical-conductor rule. Exactly the plausible-looking guess a prompt cannot prevent. | The node **validates the returned code against the rule table and overrides anything absent to `CLASSIFICATION_UNAVAILABLE`**. A prompt is a request; membership in the dataset is the only thing that counts. Confidence is also zeroed on override, since a rejected code says nothing about confidence in the final answer. **This did not fix the case that motivated it** — `8544.42` is *in* the table, so the guard passes it. See "The HS guard is narrower than I had claimed" below; I wrote this row believing otherwise. |
| **VERIFY produced noise on first live run** | First real M001 run flagged `China, Germany, Netherlands` as "unrecognised origins". | Those are correctly-identified foreign countries, not extraction errors. VERIFY exists to *save* reviewer attention and was spending it. | Split origin resolution into **eligible / external / unknown**. Only genuinely uninterpretable strings now raise a flag; recognised imports pass silently. Added `known_external_origins` to the data file and a regression test (`test_routine_imports_do_not_raise_a_review_flag`). **This node changed because of an observed problem, not a predicted one.** |
| **Origin alias layer justified itself** | Added fuzzy origin matching (aliases, "City, Country", embedded country names) as cheap defence. | The live extraction returned **"Ivory Coast"**, not the dataset's "Cote d'Ivoire". Without the alias map, M001's RVC would have silently dropped from 79.41% to 54.9% and still looked plausible. | Kept. A silently-wrong percentage is this product's worst failure mode, so defence at the origin boundary is worth its ~30 lines. |
| **GENERATE_REPORT: structure over instruction** | Could have asked the model to restate the figures accurately. | The baseline's whole failure mode is confident fabricated numbers. | The report's numeric fields are **assembled from state in Python**; the model writes only named prose fields. There is no code path from a model token to a reported figure. ## What changed reactively vs. what was designed up front

**Designed up front:** deterministic arithmetic, deterministic lookup, typed state with
`extra="forbid"`, the `CLASSIFICATION_UNAVAILABLE` sentinel, the human interrupt.

**Changed because a run showed a problem:**
- VERIFY's origin flagging (noise on first live run → three-way classification)
- Confidence zeroing on HS override (a rejected code was carrying forward a confidence score that described a different answer)
- `_step_summary` printing a total cost that isn't populated yet at EXTRACT time
- `--list` crashed on argparse's required-source group — found by running a command I had already written into REPRODUCTION.md
- A JSON `null` narrative field shipping the literal string `"None"` as a report summary — found by the hostile-narrative test, not by reading the code
- The narrative asserting legal clearance, and the `limitations` field never being rendered — both found by reading a real report end to end, not by reading `render_report`

**Deliberately not built:** retry/backoff (no failures observed), LangGraph (no branching
need), cloud escalation (local model sufficient), the 1.5B model (no experiment justified
it), cryptographic signing (explicitly out of scope — the output is a draft assessment,
not a certificate).
